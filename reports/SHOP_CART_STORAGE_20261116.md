# 우리숍 여러 탭 장바구니 저장 보존 — 2026-11-16

## 재현한 문제

기준은 고객 화면 PR #14의 62331d76df5f488a1067970c602d2aa020aa577c다. 늦은 응답을 걸러도 서로 다른 탭이 같은 localStorage 목록을 읽고 각각 덮어쓰면 한쪽 추가가 사라졌다. 실제 Edge 두 탭의 저장 직전을 CDP 중단점으로 멈춰 A에 B와 C를 각각 담았을 때 한쪽 상품이 누락되는 경로를 재현했다. 수정 뒤 같은 중단점에서 둘째 탭은 기다리고, 첫 저장 뒤 최신 목록으로 이어 써 A·B·C를 모두 보존했다.

기존 저장 도우미가 저장 거절을 삼키던 경로도 바꾼다. 저장되지 않았는데 담았다고 알리거나 주문 준비를 진행하지 않는다. 고객 정보·운영 연결은 사용하지 않았다.

## 변경한 계약과 화면

새 cart-store.js가 같은 출처의 작성자를 하나의 Web Locks 이름으로 묶는다. 잠금을 얻은 뒤 최신 목록을 읽고, 동기 계산과 저장을 마친 뒤 놓는다. 네트워크나 사용자 입력을 기다리며 잠금을 잡지 않는다. 5초 동안 얻지 못하면 해당 대기를 취소하며 강제로 다른 탭의 잠금을 빼앗지 않는다. 도구 누락·저장 권한/용량 오류·손상된 자료는 보류하고 원문을 보존한다.

상품 상세·장바구니 수량/삭제/되돌리기·찜에서 담기·서가의 세 가지 담기·재고/견적 반영·주문 준비/완료·시험 계정 정리를 같은 저장 경로에 연결한다. 화면에서 성공을 알리는 시점은 저장 성공 뒤다. 서가는 기다리는 동안 중복 누름을 막고 실패 후 다시 시도할 수 있다. 이미 닫힌 서가에는 뒤늦게 성공 표시를 붙이지 않는다. 비동기 담기를 이해하지 못하는 오래된 서가 모듈과 섞였을 때는 새로고침을 안내한다.

주문 준비는 보여준 목록과 최신 저장 목록을 잠금 안에서 비교하고 줄 식별자를 저장한 뒤 접수 장부로 넘어간다. 대기 중 늦은 쿠폰 응답이 와도 클릭 당시 확인한 요청의 내용·합계를 바꾸지 않는다. 완료 정리는 같은 잠금 안에서 영수증, 장바구니 순으로 쓴다. 두 저장은 하나의 원자적 거래가 아니다. 주문 장부의 완료 결과와 줄 식별자를 남겨 부분 실패 뒤 같은 결과로 다시 정리하며, 정리 실패 중 새 주문 시작은 보류한다. 접수된 주문의 조회 링크는 계속 제공한다.

시험 계정의 옛 401 응답은 새 로그인 열쇠를 지우지 않는다. 정리 대기 중 로그인이나 장바구니가 바뀌면 해당 자료를 보존한다. 기존 계정 화면 전체의 비동기 응답 소유권까지 고쳤다는 뜻은 아니다.

## 남은 경계와 적용 순서

Web Locks는 같은 이름의 잠금을 요청하는 새 코드끼리만 조정한다. 잠금을 사용하지 않는 오래된 탭·다른 출처·다른 기기를 이 잠금으로 제어할 수 없다. 배포 전에 shop.js·cart-store.js·shelf.js·shop-acct.js의 캐시 혼재, 지원 브라우저/보안 문맥, 구버전 탭 갱신 정책을 확인해야 한다. 저장을 막는 브라우저에서는 읽기/둘러보기는 가능하지만 장바구니 변경·주문 준비는 진행하지 않는다.

#5→#9→#10→#12→#14 뒤 최신 main에 이 변경을 통합하고 PR 대상을 main으로 바꾼다. 부모 작업 가지로 병합하지 않는다. 서버 #5→#6→#11→#13과 시험 게이트·CI의 합집합을 유지한다. Claude가 비공개 통합·실기기·캐시 전환·판 번호·빌드·제한 배포를 맡는다. 수량 예약 활성화는 계속 OFF다. 운영 주문·계정·자료·배포·판 번호·수집기 머리는 변경하지 않았다.

## 설계 근거

같은 출처의 탭/워커가 공유 자원을 독점하고 콜백 완료 뒤 잠금을 놓는 Web Locks 계약을 적용했다. 잠금 없는 옛 코드까지 보호한다고 해석하지 않는다. [MDN Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API), [MDN LockManager.request](https://developer.mozilla.org/en-US/docs/Web/API/LockManager/request).
