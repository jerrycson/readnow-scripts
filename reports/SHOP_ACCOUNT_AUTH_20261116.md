# 우리숍 최신 세션 인증과 인증 실패 시 주문 보류 — 2026-11-16

서버 PR #23 dd410b4d5a8ef9c7949321535585c1710df26d5a에서 시작했다. 서버 결함 5건의 재현·수정과 공개 회귀 검증은 끝났다. 최신 고객 화면을 합친 추가 검사에서 새로고침 후 앞선 회원 주문을 비회원으로 재시도하는 문제가 남았다. 이 문서는 초안 검토 결과이며, 고객 주문 소유권 후속 수정과 tACCOUNTAUTHUI 통과 전 운영 반영을 보류한다.

## 확인한 결함과 수정

다른 서버가 로그아웃을 저장해도 기존 서버의 30초 회원 캐시가 새 회원정보 조회와 찜 저장을 허용했다. 두 독립 재현은 원본 0/2 → 수정본 2/2다. 인증 함수는 매 요청 최신 회원 문서를 읽고, 회원 번호·계정 상태·세션 해시·만료를 기존 거래용 검증 함수로 확인한다. 조회 실패를 오래된 성공 캐시로 대신하지 않는다. 회원 표시용 캐시는 남긴다.

주문 함수는 인증 읽기 실패를 비회원으로 취급했고, 폐기된 인증 열쇠도 비회원 접수로 바뀌었다. 인증 뒤 접수 거래 전에 세션이 폐기돼도 주문과 예약이 저장됐다. 이 세 독립 재현은 원본 0/3 → 수정본 3/3이다. 운영 발생을 단정하지 않는다.

주문 인증 읽기 실패는 503(authPending), 인증 머리가 있으나 현재 유효하지 않으면 401(login)로 접수를 보류한다. 두 경우 주문·예약·요청 결과 기록을 쓰지 않으므로 나중에 같은 요청 번호로 확인·재시도할 수 있다. 인증 머리가 없는 비회원 주문은 기존처럼 처리한다. 인증한 회원 주문은 접수 거래가 읽은 최신 회원의 세션까지 확인한다. 그 사이 폐기·만료·보관·탈퇴 등이 생기면 403 거절 결과를 원래 요청 기록에 확정하고 주문·예약은 쓰지 않는다.

이미 커밋된 주문은 원래 요청 확인 키로 결과를 조회할 수 있다. 인증 조회 실패나 이후 로그아웃 때문에 이미 끝난 주문을 새로 접수하지 않는다. 같은 회원의 다른 유효한 기기에서 재전송해도 기존 요청 결과를 유지한다. 다른 기기만 로그아웃한 경우 현재 기기의 주문은 허용한다.

## 검증

- 독립 인증 캐시 재현 0/2 → 2/2, 실제 주문 함수 경계 재현 0/3 → 3/3.
- 새 회원 인증·주문 회귀 58/58. 새 조회·저장·사진, 다른 서버 로그아웃·비밀번호 교체, 손상·만료·폐기 세션, 읽기 실패, 접수 거래 재실행, 응답 결과 복구, 실제 HTTP 503/401/200·no-store를 포함한다.
- 핵심·구문 326/326, 이전 출고·재고·노트·최신 고객 변경 통합 핵심·구문 403/403.
- 최신 고객 코드를 합친 tSHOP9_1112 전체 HTTP·UI 통과. 화면 오류·alert/confirm 0.
- tSHOPVIEW2_1114 합성 HTTP 통과. 시험 계정의 주문 403과 기존 제한 유지.
- 실제 주문 서버·고객 복구 통합 tACCOUNTAUTHUI는 7/8. 아래 새로고침 사례 1건 실패(종료 코드 1). 전체 통합 성공으로 집계하지 않는다.
- 기존 주문 원자성 시험의 합성 인증 객체에 최신 세션 검사와 유효한 세션 자료를 추가했다. 이 시험은 거래·중복 방지를 검사하며, 새 account-auth 시험은 실제 회원 인증 함수를 사용한다.

관련 파일 6경로를 tACCOUNTAUTH·tACCOUNTAUTHUI·tACCOUNTSESSION·tORDERRETRY 및 기존 회원 시험에 연결했다. 공개 CI의 standalone과 기존 회원 UI가 통과해도 새 통합 화면 검사가 완료됐다는 뜻이 아니다. tACCOUNTAUTHUI는 서버와 최신 고객 복구 의존 PR을 합친 작업본에서 필수로 실행한다. 비공개 전체 배포 게이트 자체는 실행하지 않았다.

초기 확장 브라우저 재현은 토큰 저장 키를 bq-token으로 잘못 적어 비회원으로 실행됐다. 로그를 보존하고 실제 bq-tok과 저장 확인을 사용해 재검사했다. 보정 후 기존 다섯 복구 사례와 인증 실패/같은 계정 재시도, 폐기 세션의 현재 화면 재시도는 7/7이었다. 이어 새로고침 조건을 추가하자 그 사례만 실패했다. 시험 틀 오류와 실제 후속 결함을 구분했다.

## 아직 실패하는 고객 복구 조건

1. 회원으로 주문을 보내기 직전에 서버에서 해당 세션이 폐기된다.
2. 서버는 새 접수를 401로 막고 고객 화면은 원래 요청 번호를 보존한다.
3. 새로고침 시 회원 조회가 401을 확인해 기기 토큰을 정리한다.
4. 앞선 주문의 같은 내용 입력·재전송을 누르면 현재 비회원 상태로 주문이 새로 접수된다.

주문 복구 장부가 시작 당시 계정을 보존하지 않아 생기는 후속 문제다. 처음부터 비회원으로 시작한 주문은 계속 허용해야 한다. 회원 주문은 같은 회원의 새 로그인으로만 이어가고, 계정이 바뀌면 앞선 결과 조회·미접수 닫기는 유지하되 다른 계정/비회원으로 재전송하지 않도록 다음 고객 PR에서 보완한다. 이 조건을 tACCOUNTAUTHUI에 기대값을 낮추지 않고 남겼다.

## 근거와 읽기 비용

[Firebase 세션 관리 문서](https://firebase.google.com/docs/auth/admin/manage-sessions)는 세션 폐기 확인에 최신 서버 상태가 필요하고 추가 네트워크 비용이 있음을 설명한다. 리드나우는 자체 세션 해시 방식을 유지하며 이 원칙만 적용한다. Firebase Authentication으로 옮긴 것이 아니다. [OWASP 세션 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)의 서버 측 로그아웃 무효화 원칙도 참고했다.

인증 함수 자체의 합성 계측은 유효한 인증 요청 4회에 회원 읽기 4회, 잘못되거나 없는 인증 형식은 읽기 0회다. 30초 캐시를 재사용하던 인증 경로보다 읽기 수가 늘어난다. 이 변경을 성능 개선으로 주장하지 않는다. 실제 지연·읽기 비용·분석 수집 요청의 부하는 Claude가 제한 적용 전 측정해야 한다. 주문 거래의 회원 읽기는 기존 목록 보존 거래에서 이미 하던 읽기를 사용해 검증한다.
