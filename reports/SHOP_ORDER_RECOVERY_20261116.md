# 우리숍 주문 요청 보존과 복구 화면 — 2026-11-16

## 변경과 의존

고객 화면 PR #10의 80b79d44를 기준으로 한다. 서버 요청 계약 PR #11이 먼저 적용되어야 한다. 서버 지원 표시가 없거나 주문 장부를 저장하지 못하면 전송을 시작하지 않는다. 새 경로가 없는 서버에서도 기존 주문 경로로 우회하지 않는다. 운영 설정·판 번호·배포 결과물은 바꾸지 않았다.

한 구매의 요청 번호·비밀값·내용 해시·제출 장바구니 줄 식별자를 IndexedDB에 먼저 저장한다. 이름·주소·연락처·동의·쿠폰·요청 본문은 이 장부에 저장하지 않는다. 기존 sessionStorage 입력 초안은 유지하며 동의 칸은 다시 확인한다. 서버와 같은 구매 내용을 구분하는 데 쓰는 해시 외에 개인정보 원문을 추가로 영속 저장하지 않는다.

실제 IndexedDB readwrite 거래와 strict 저장 완료 뒤에만 새 접수를 보낸다. 같은 출처의 두 탭은 진행 요청 하나를 공유한다. 완료/확정 거절을 확인한 뒤 다음 구매를 열 때 화면 번호를 올려 오래된 주문서가 새 접수를 만들지 못하게 한다. 닫은 요청 기록과 완료 조회 영수증은 보존한다.

응답 유실·저장 실패·지원 표시 없는 응답은 미확정으로 유지한다. 주문서 재진입·새로고침은 POST /shop/order-status로 결과만 확인한다. absent는 자동 재전송 근거가 아니다. 사용자가 같은 내용을 다시 제출하면 원래 요청 번호·비밀값을 사용하고 내용 해시를 확인한다. 가격·주소·수량이 바뀌면 전송하지 않는다.

미접수 요청 닫기는 서버의 POST /shop/order-close를 사용한다. 접수와 닫기가 경합하면 같은 요청 문서에서 먼저 확정한 결과를 따른다. 이미 접수되었으면 완료 주문을 보여주며 취소하지 않는다. 닫기 결과까지 확인되어야 새 내용을 작성할 수 있다. 닫기 응답이 불명확하면 진행 요청을 유지한다.

완료 뒤에는 제출한 장바구니 줄·수량만 정리하고 새 입력 초안을 보존한다. 요청 장부에 완료 기록을 먼저 남기므로 로컬 표시 갱신이 실패해도 같은 접수를 다시 만들지 않는다. 복구 화면은 장바구니가 비거나 가게 설정이 닫혀도 먼저 확인할 수 있다.

## 적용 근거와 남은 검증

[MDN IndexedDB 거래 설명](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction)과 [거래 저장 옵션](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction)에 따라 같은 저장소 쓰기를 거래로 직렬화하고 완료 전에는 외부 주문을 보내지 않는다. localStorage의 별도 읽기·쓰기를 주문 선점 장치로 사용하지 않는다.

이 장부는 같은 브라우저 출처의 정상적으로 보존된 저장소 범위다. 기기·다른 도메인·브라우저 데이터 삭제 사이의 동일 구매 인식까지 보장하지 않는다. strict IndexedDB 또는 안전한 난수/해시를 사용할 수 없으면 안내 후 주문을 보류한다. 지원 기기 범위는 실제 운영 기기에서 확인해야 한다.

실제 Firestore·인증·운영 규칙·비공개 통합·실기기·서버/정적 파일 캐시 혼재는 미확인이다. 화면 회귀 52개는 합성 계약 응답이며 별도 종단 5개는 실제 서버 함수를 로컬 HTTP로 호출한다. 저장소는 합성이므로 실제 Firestore의 규칙·경합 확인은 남아 있다. 기존 다른 탭 localStorage 장바구니 편집 경합은 별도 검토 대상으로 남긴다. 계정 보조 주문 목록 복구도 서버 PR에 남아 있다.
