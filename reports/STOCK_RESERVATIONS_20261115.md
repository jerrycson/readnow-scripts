# 수량별 예약 구현과 활성화 조건

출고 안정화 PR #5 이후 적용하는 별도 묶음이다. 기본 설정은 기존 상품 전체 잠금이다. 운영 예약 이관·설정 변경·실제 주문 생성은 하지 않았다.

## 저장 계약

- `shop_holds/{listingId}`: `schema:2`, `basis:{kind:'physical-total',qty,observedQty,evidence,actor,at}`, `reservedQty`, `committedQty`, `review`.
- `shop_reservations/{encodedListingId}__{encodedOrderNo}`: 주문별 수량·상태(`reserved/released/committed`)와 변경 시각. 취소해도 삭제하지 않는다.
- `shop_stock_audit/{hash}`: 이관·실물 재확인의 이전/다음 값과 확인 근거. 고객 연락처는 이 도구의 입력으로 받지 않는다.
- schema 2의 `on:1`은 이전 판이 상품 전체를 잠그도록 유지한다. 새 판만 합계와 판매 가능 수량을 해석한다.

## 실제 경로

주문 생성은 상품·예약 합계·기존 주문별 예약을 먼저 읽고 주문과 예약을 같은 트랜잭션에 저장한다. 손님 취소와 관리자 취소는 해당 주문 예약만 같은 트랜잭션에서 해제한다. 관리자 확인 중 입금 상태가 바뀌면 확인했던 상태와 다른 취소를 진행하지 않는다. 출고로 보내기는 예약을 판매 확정 수량으로 옮기며, 오래된 판매처 수량을 다시 판매하지 않는다. 중복 취소·중복 확정은 수량을 두 번 반영하지 않는다.

웹앱과 서버는 `cloud/shop-stock.js`의 같은 순수 계산을 사용한다. Hosting 허용 목록에도 해당 파일을 추가한다. 기존 형식만 읽는 주문은 새 예약 컬렉션을 추가로 조회하지 않는다. 공개 목록의 20초 캐시는 유지하며 최종 주문 트랜잭션이 마지막 수량을 다시 확인한다.

## 수량 기준: 활성화 전 확인 필요

판매처 수량은 우리숍 예약 동기화 후 잔량일 수도 있다. `현재 수량 - 예약`을 무조건 적용하면 이중 차감한다. 반대로 모든 감소를 자체 예약 반영으로 가정하면 외부 판매를 놓친다.

이 구현은 확인한 실물 총량과 그때 관찰한 판매처 수량을 함께 저장한다. 관찰 수량이 바뀌면 새 확인 근거가 생길 때까지 판매를 보류한다. 일치할 때만 `min(관찰 수량, 실물 총량 - 예약 - 판매 확정)`을 쓴다. 외부 판매 표는 기존 예약을 덮지 않고 재고 확인 대상으로 만든다.

**제한:** 판매처 동기화 결과를 자동으로 새 기준에 연결하는 운영 경로는 아직 검증되지 않았다. 이 상태에서 수량별 판매를 전면 활성화하면 동기화 후 확인 대기가 잦아질 수 있다. 실제 판매처의 총량/잔량 의미와 예약·취소·판매·반품의 반영 근거를 대조하고, 해당 결과를 원자적으로 재확인하는 경로를 연결한 뒤 제한 활성화해야 한다. 현재 초안 PR은 활성화 준비 및 안전한 이관 기반이다.

## 이관·재확인 도구

`cloud/shop-stock-admin.js`는 운영자 라이브러리이며 HTTP 경로를 추가하지 않는다. `change(db, input)`은 기본 미리보기다. 상품, 확인 근거, 담당, 실물 수량, 관찰 수량이 필요하다. 적용에는 미리보기의 `stateHash`를 `expectedStateHash`로 전달하고 `apply:true`를 지정해야 한다. 상태나 관찰 수량이 바뀌면 전체 거래를 거절한다. 같은 근거를 다른 수량으로 재사용해도 거절한다.

이관은 대응 주문이 `new/paid`이고 각 품목 수량이 명확할 때만 예약을 만든다. 대응 주문·수량이 없거나 출고 후 수량 의미가 불명확하면 전체 잠금과 확인 표시를 보존한다. 이미 수량 형식이면 `mode:'reconcile'`과 새로운 확인 근거로만 실물 기준을 갱신한다. 적용과 감사 기록 저장은 같은 거래다.

## 적용 순서

1. PR #5 통합 시험 후 이 변경의 서버·관리 화면·공유 모듈·Firestore 규칙을 함께 검토한다. 새 컬렉션의 읽기/쓰기는 기존 관리자 범위를 따른다.
2. 모든 예약 작성 경로가 새 형식을 처리하는지 확인하고, 이전 관리 탭/서버가 계속 쓰지 않도록 판을 맞춘다.
3. 원본 예약을 보존한 이관 미리보기를 검토한다. 확인 불가 항목은 잠금을 유지한다.
4. 판매처 동기화와 외부 판매·반품의 수량 증거 연결을 구현·통합 검증한다. 운영자 재확인만으로 전면 활성화하지 않는다.
5. 확인된 소수 상품에서 `app_settings/shop.quantityReservations:true`를 제한 적용한다. 3권 중 1권 예약 뒤 2권 가능, 마지막 수량 경합, 취소·입금 경합, 판매 확정·외부 판매·반품을 확인한다.
6. 되돌릴 때 설정을 끄고 예약·감사 기록을 남긴다. 진행 중 상품은 전체 잠금으로 돌아간다. 배포 코드를 되돌리는 것과 예약 자료를 삭제하는 것을 혼동하지 않는다.

## 검증

가짜 Firestore를 이용한 독립 시험 20건 통과. 실제 주문 함수와 손님 취소 함수도 추출하여 실행했다. 운영 Firestore 규칙, 여러 서버 판 혼재, 실제 결제·판매처 동기화·반품은 아직 검증하지 않았다.

설계 근거: [Shopify의 예약 일관성 사례](https://shopify.engineering/scaling-inventory-reservations), [Firestore 트랜잭션의 재시도와 읽기/쓰기 순서](https://firebase.google.com/docs/firestore/manage-data/transactions). 데이터베이스 교체 없이 주문별 예약과 합계의 원자성만 적용한다.
