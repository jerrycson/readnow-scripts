# 우리숍 주문 재시도 서버 계약 — 2026-11-16

## 확인한 위험

기반은 수량 예약 PR #6의 06222003이다. 공개 가짜 저장소에서 한 구매 결정의 첫 응답이 유실되어 동일 요청을 다시 보낸 상황을 만들었다. 기존 전체 잠금은 200 → 409로 주문 하나만 남겼지만 원래 결과를 되돌려주지 못했다. 수량 예약을 켠 가짜 환경은 200 → 200으로 서로 다른 주문 두 개·예약 두 개를 만들었다. 운영 설정과 자료는 변경하지 않았다.

## 계약과 구현

- 기존 POST /shop/order는 수량 예약 OFF에서 옛 요청을 계속 받는다. quantityReservations가 true이면 요청 계약 없는 주문을 접수 전에 거절한다. 활성화 기본값과 운영 설정은 바꾸지 않았다.
- 새 접수는 POST /shop/order-attempt, 결과 조회는 POST /shop/order-status다. 두 경로는 POST만 받으며 no-store 응답을 사용한다. 옛 서버에는 이 경로가 없어 새 클라이언트 요청을 일반 주문으로 오해하지 않는다. 공개 설정 orderProtocol: 1로 지원 여부를 알린다.
- 접수 본문은 기존 주문 필드에 attempt: { id, secret }을 더한다. id는 무작위 16바이트의 소문자 hex 32자, secret은 무작위 32바이트의 hex 64자다. 고객 화면은 암호학적 난수로 한 구매 결정마다 한 쌍을 만들고 결과 불명 동안 바꾸지 않아야 한다. 번호만으로 결과를 조회할 수 없다.
- 요청 내용은 기존 checkOrder의 정규화 결과와 로그인 사용자 번호를 정렬된 객체 형식으로 해시한다. 전화 표시나 객체 속성 순서는 같게 처리하되 상품/수량/주소/쿠폰/기대 합계/사용자가 달라지면 충돌로 거절한다. 별도 요청 번호의 같은 내용 구매는 서로 다른 구매다.
- 주문·주문별 예약·shop_order_attempts 결과 기록을 같은 Firestore 트랜잭션에 쓴다. 저장 실패 때는 모두 반영되지 않는다. 거래 재실행·서로 다른 서버 동시 접수도 요청 문서를 먼저 확인한다. 확정 거절도 기록하므로 늦은 재제출이 나중에 주문으로 바뀌지 않는다. 형식/동의 등 사전 검증 오류와 호출 제한은 주문을 쓰지 않는다.
- 완료/거절의 재요청은 원래 결과를 반환한다. 가게 닫힘·재고 소진·할인 만료 뒤에도 기존 결과를 조회할 수 있다. 결과 조회는 completed / rejected / absent 상태를 돌려주고 주문을 만들지 않는다. absent는 현재 기록이 없다는 관찰이며 다른 요청이 전송되지 않았다는 증거가 아니다. 재전송이 필요하면 같은 쌍과 같은 내용을 유지해야 한다.
- 비밀값 원문·조회 토큰 원문·주문자 정보는 요청 문서에 저장하지 않는다. 비밀값 해시와 요청 해시, 공개 주문 결과만 보관한다. 기존 조회 토큰은 비밀값과 요청/주문 번호로 HMAC-SHA256을 계산해 재구성하며 기존 32자리 형식과 bq 접두사 토큰 해시를 유지한다. 주문 문서에는 해시만 저장한다. 비밀값을 URL/로그에 넣지 않는다.
- 연결 주문이 없거나 토큰 해시/기록 형식이 맞지 않으면 확인 대기로 남긴다. 기록을 지우고 새 주문을 만들지 않는다. 취소 후 재조회도 원래 접수 결과만 반환하며 재예약하지 않는다. 현재 주문 단계는 기존 GET /shop/order로 확인한다.

## 근거

[AWS 공식 재시도 설계](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)의 고객 요청 식별자·내용 일치·같은 거래의 결과 기록 원칙을 적용했다. 내용 해시만으로 별도 구매를 중복이라 추정하지 않는다. [Firestore 공식 거래 안내](https://firebase.google.com/docs/firestore/manage-data/transactions)에 맞춰 읽기 다음 쓰기 순서와 거래 재실행을 검사했다. 분산된 판매처 외부 쓰기와 달리 이 단계의 주문·예약·요청 결과는 같은 Firestore 안에서 함께 확정한다.

## 배포 순서와 남은 일

이 서버 PR은 #6에 의존한다. #5 → #6를 main에 반영한 뒤 이 PR 대상을 main으로 바꾼다. 자식 PR을 부모 작업 가지에 합치지 않는다. Claude가 통합·판 번호·실제 배포를 맡는다.

고객 화면의 영속 요청 저장, 새 경로 호출, 결과 불명 표시와 조회/복구 연결은 다음 작업이다. 현재 PR #10 고객 화면은 아직 새 계약을 사용하지 않는다. 서버 지원 배포 → 고객 화면 연결 → 옛 고객/서버 혼재·응답 유실 통합 검사 → 제한 적용까지 확인하기 전에는 수량 예약 OFF를 유지한다.

shop_order_attempts는 서버 전용 컬렉션이다. 운영 Firestore 규칙의 직접 고객 읽기/쓰기 차단을 Claude가 확인해야 한다. 기록 만료/청소는 추가하지 않았으며 기록 삭제 뒤 같은 요청 번호를 다시 접수하는 경로를 만들지 않는다. 고객 화면은 원본 개인정보·동의 상태를 새 영속 저장소에 추가하지 않는 방향으로 연결한다.

계정의 주문 목록 추가는 기존대로 주문 거래 뒤 별도 처리된다. 거래 확정 뒤 프로세스가 끝나면 이 계정 보조 목록이 빠질 수 있다. 주문·예약·요청 결과와 uid는 보존되지만 계정 목록 복구는 별도 검토 대상이다. 운영 비공개 통합 시험·실기기·실제 Firestore·규칙·캐시/서버 혼재는 아직 미확인이다.
